## What the product is now (availability model)

The first design counted stock per product. It was replaced (decision of 2026-10-30, "hybrid layers 1 + 2 + 3", details in `availability_design.md`) by an availability model that never stores quantities:

1. **The pharmacy's list**: for each catalogue medicine, *available / unavailable*, a price and the time a pharmacist last confirmed it. Filled by Excel/CSV import (names matched to the catalogue on the server, reviewed by the pharmacist), one by one, and by answering customers' questions.
2. **Customer search**: only confirmed pharmacies are listed, nearest first when the customer's location is known, each with its freshness (`recent` ≤ 7 days, `old` ≤ 30 days; older listings are hidden).
3. **"Ask the pharmacies nearby"**: pharmacies within 1 km are notified and answer *available (with price)* / *unavailable*; the server widens the circle 1 → 3 → 5 → 10 km (empty circle, everybody said no, or 3 minutes of silence) and the customer can widen it by hand.

Orders are a **promise**: when a pharmacy accepts, it promises to prepare the order for 24 hours. No counter is decremented anywhere.

## Defects found by the SQL tests and fixed (kept here on purpose)

1. **Internal `private.*` functions were executable by everyone.** `ALTER DEFAULT PRIVILEGES IN SCHEMA … REVOKE` cannot remove PostgreSQL's built-in PUBLIC execute default. Fixed with a global default revoke plus a final sweep (found by `t_sec_01`).
2. **Malformed cart (`[1,2]`) raised a raw SQLSTATE 22023** instead of `invalid_input` (found by `t_pos_04`). `parse_items` now checks element types.
3. **`get_sale` answered `forbidden` for another pharmacy's receipt**, revealing that the id exists. Now `not_found` (found by `t_pos_07`).
4. **Race: a customer could exceed the 5-pending-orders cap by sending requests in parallel** (9 pending created). Fixed with a per-customer row lock in `create_order` (found by concurrency scenario s9); `create_availability_request` takes the same lock for its open-request and hourly caps.
5. Weak spots in the test suite itself were found by the mutation check (the order trigger and the `private` grants were only protected by redundant guards that hid the gap); tests were added and the mutations made stricter. The current run has 46 mutants, none surviving.
6. **Wrong claim in a Dart comment (found 2026-10-31 while writing these docs):** `SalesRepository.createPosSale` said the server answers `price_changed` on a price mismatch. `create_pos_sale` does not compare prices at all; the comment and `database_schema.md` were corrected (see known issue 5).

## Known issues / limitations

1. **All Dart code is uncompiled** (see above). This is the single biggest risk.
2. **No `android/` / `ios/` projects** in the repository; generate them with `flutter create` and apply the platform notes in `release_checklist.md` §2: file picker, printing, url_launcher, `--dart-define`, and the **location permissions** (Android `ACCESS_FINE_LOCATION` / `ACCESS_COARSE_LOCATION`, iOS `NSLocationWhenInUseUsageDescription`).
3. **Password recovery is incomplete in the app.** The reset e-mail is requested (`resetPasswordForEmail`) but no redirect URL or deep link is configured and there is no "choose a new password" screen: the link opens whatever the Supabase *Site URL* points to. Decide on a hosted page or add deep-link handling before release (`release_checklist.md` §1).
4. **Manager vs owner on pharmacy settings.** `RoutePolicy` lets managers open the profile / contact / hours settings screens, but `update_my_pharmacy` is owner-only in the database. The screens are read-only for managers (the controller's `canEdit` is owner-only), so nothing can be changed by mistake; the route guard is simply looser than the server.
5. **`create_pos_sale` ignores `expected_unit_price`** (the server always prices from the list row; `create_order` does compare and answers `price_changed`). If a price changed after the POS list was loaded, the basket shows the old price until it is refreshed; the sale and the receipt always carry the server's price.
6. **Cashier answers do not update the list.** When a cashier answers a customer's request, the answer is stored on the request only; only an owner or manager answer also updates `pharmacy_products`. As a result an offer may have no matching list row (or a different price), so the customer's "reserve" button is hidden or the order is revalidated by `create_order` (`product_unavailable` / `price_changed`).
7. **Scheduled jobs are documented, not created.** Three `pg_cron` jobs are needed (`release_checklist.md` §1): `private.expire_all_reservations()` every 5 minutes, `private.advance_all_availability_requests()` every minute, and the idempotency-key purge daily. Without them: reservations still end lazily (acceptance, POS sales and the orders screen sweep their own pharmacy) and every read of a request applies widening/expiry, but requests of customers whose app is closed are not advanced, and `idempotency_keys` and old requests grow.
8. SQL was verified against a stub, not real Supabase; `supabase/config.toml` is unvalidated.
9. Searching a very common 2-letter fragment over ~30k catalogue rows takes ~0.35–0.4 s (ranked by similarity; 406.7 ms in the last run); acceptable for the MVP, revisit with a `pg_trgm` `%` pre-filter or a minimum token length of 3 if the catalogue grows.
10. Concurrency and mutation tools need a superuser connection to a local PostgreSQL ≥ 15; they are not wired into CI.
11. Notifications are in-app only (a list screen plus an unread badge that is refreshed when the screen is opened and after relevant actions, not live); **there is no push delivery**, so a pharmacy only sees a customer's question when it opens the app (the requests screen polls while open). Push is optional and described in `release_checklist.md`.
12. Admin area by design: customers' accounts are not listed to administrators (privacy), so audit entries made by customers show no actor name; archiving a medicine cannot be undone from the app (the database has no transition out of `archived`); the licence document opens in an external app through a 10-minute signed link; the admin pharmacy details screen does not show the shop's location yet.
13. Legal texts (privacy policy, terms) are placeholders and need review by counsel (`requirements.md` Q-06). They must also mention that the customer's approximate location (rounded to ~100 m) is sent to the server to find pharmacies and is never shown to pharmacies.
14. The customer's position is rounded to 3 decimals on the server and is stored with the request for up to 30 days (then deleted by the sweeper). Decide whether that retention is acceptable.
